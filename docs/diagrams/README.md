# Architecture diagrams

AWS-style architecture diagrams of the estate, rendered from code with the
official AWS icon set (the [`diagrams`](https://diagrams.mingrammer.com/) library
over Graphviz). Generated by [`scripts/gen_diagrams.py`](../../scripts/gen_diagrams.py).

Each environment is drawn from **three perspectives**, so a reader is not
overwhelmed by every edge at once. **All three are auto-derived** from the infra.

Diagrams are split into two folders by how they are produced:

- **`auto-derived/`** — generated from the infra; do not edit by hand.
- **`curated/`** — reserved for any future hand-authored diagram; currently none. The README's
  hand-built overview is [`../images/architecture.svg`](../images/architecture.svg).

| View | File | Shows |
|---|---|---|
| **Overall** | [`auto-derived/dev-architecture.png`](auto-derived/dev-architecture.png) | Every component (icon per module) + the dependency edges between them, clustered by tier, **transitively reduced** so only direct dependencies are drawn. |
| **Security** | [`auto-derived/dev-security.png`](auto-derived/dev-security.png) | Encryption at rest (KMS CMK `encrypts` its data stores + workloads), in transit (TLS legs, with port), secret access (`secrets` dep → "reads secret"), and no public ingress (`ingress_mode = "ssm"`). |
| **Data-flow** | [`auto-derived/dev-dataflow.png`](auto-derived/dev-dataflow.png) | Runtime service calls (scheme + port) and object-store access (workload → `data/s3` bucket, **read-only vs read/write**), plus the SSM ingress. |

All three read the same parsed model ([`src/iac/diagrams/derive.py`](../../src/iac/diagrams/derive.py)),
so adding or rewiring a component changes the diagrams automatically — they cannot
drift. The **overall** view uses the `dependency` edges; the **security** and
**data-flow** views classify those dependencies semantically (a `kms` dep →
"encrypts", a `secrets` dep → "reads secret", a `data/s3` dep → data access) and add
the runtime connections parsed from each component's `inputs`.

### How a connection is recognised

The estate writes a connection two ways, and **both** are parsed — reading only the
first made the views silently omit whole subsystems (XbrlRag appeared to touch neither
Qdrant nor its own database):

- **One URL** — `MACRORAG_QDRANT_URL = "https://qdrant.<ns>.internal:6333"`.
- **A `<PREFIX>_HOST` / `_PORT` / `_HTTPS` / `_SSLMODE` env-var group** — XbrlRag's
  idiom, for both Qdrant and Postgres. The host is often not a literal at all but
  `dependency.db.outputs.address`; such a reference is resolved through that
  dependency block's `mock_outputs` (the one place the HCL states the value
  offline) and names its target component directly, no DNS lookup involved.

A caller is matched to the component it reaches by the **Cloud Map name** — i.e. the
module's `app_name`/`discovery_service_name`, not the folder name, so
`arag.<ns>.internal` resolves to `42-arag/app` (three tiers all have a folder called
`app`; only one is named `arag`).

Readability and honesty filters, all tested: a component switched off by `ingress_mode`
is left out, because its folder stays when its resources don't (the ALB under `ssm`);
KMS `encrypts` is drawn to data stores
+ stateful workloads only (not schedulers/NAT); only workloads draw S3 data edges
(not the VPC's flow-log delivery); an S3 grant whose input name says `read`
(`bundle_read_bucket_arn`, `task_read_bucket_arns`) is labelled **read-only**, so a
workload that merely pulls its deploy bundle is not drawn as owning the bucket; and
a Postgres leg counts as TLS only for `sslmode` values that truly encrypt (`prefer`
falls back to plaintext, so it does not).

Both a **PNG** (self-contained raster, good for embedding/preview) and an **SVG**
(scalable) are written per view. The PNG is the portable artifact — see the
rendering note below for why the SVG is not yet committable as-is.

## Regenerate

```bash
# all three views for dev (writes docs/diagrams/auto-derived/dev-*.{png,svg}; contacts no AWS)
conda run -n py312 python scripts/gen_diagrams.py --env dev --view all

# a single view
conda run -n py312 python scripts/gen_diagrams.py --env dev --view security
```

The generator reads the **working tree**, so a component that is written but not yet
applied would be drawn as if it existed. Render the committed tree when a staged
sub-system is sitting in the tree — the checked-in PNG should show what is actually
in AWS, and the staged tier reappears on its own once it lands.

Requires Graphviz (`dot`) on PATH — install once into py312:

```bash
conda install -n py312 -c conda-forge graphviz && pip install diagrams
```

### Rendering note (Windows / conda Graphviz)

conda-forge Graphviz on this machine routes `-Tpng` through the **cairo** device,
which **segfaults and writes a 0-byte PNG**. The generator works around it by
rendering the PNG through the **`gd`** device instead — the only working device
that also embeds the node icon images (`gdiplus` renders, but drops the icons,
leaving text-only nodes). SVG is unaffected. The one visible cost: the `gd` raster
handles a Unicode em-dash as mojibake, so rendered labels use ASCII `-`.

The generated **SVG references the icon PNGs by absolute local path**, so it is not
portable across machines yet. The committed **PNG is self-contained**. Making the
SVG portable (inline the icons as base64) is on the roadmap below.

## Roadmap / TODO

1. ✅ **Auto-derive all three views from the Terragrunt HCL** — done (Slices 1 & 2).
   Overall = dependency graph (transitively reduced); security + data-flow =
   semantic classification of dependencies + runtime calls parsed from `inputs`.
   All tested against the real `dev` tree in
   [`tests/unit/test_diagrams_derive.py`](../../tests/unit/test_diagrams_derive.py).
2. **Refresh diagrams as part of every sub-system's definition-of-done.** When a
   sub-system's provisioning is landed and verified, re-run `gen_diagrams.py` — all
   three views update themselves from the infra — in the **same** change, exactly
   like the Layer C ledger in `scripts/postdeploy.py`. A diagram that lags the infra
   is worse than none.

   Practised for XbrlRag, and worth the warning it produced: "auto-derived" guarantees
   the diagram cannot contradict the HCL, **not** that it says everything the HCL
   does. XbrlRag's refresh only drew its database and vector-store legs once the
   derivation learned a second connection idiom. Regenerating is therefore not the
   whole job — *look at the output* and check the sub-system's real data paths are
   on it.
3. **Portable SVG** — inline the AWS icons as base64 data URIs so the committed SVG
   renders anywhere, not just on the machine that generated it.
4. **`staging` / `prod`** — the generator is already env-parameterised (`--env`);
   render those once their environment trees are populated.
5. **Ingress heuristics** — ingress is derived from `ingress_mode` + which modules
   are SSM-reachable EC2 hosts; revisit if an ALB/public path is reintroduced.

## Scope note

These are code-driven diagrams in the AWS visual language — the icon vocabulary and
the account/VPC/subnet grouping. They are deliberately **not** pixel-identical to a
hand-laid AWS marketing diagram (no bespoke callouts or hand-routed lines); the
layout is Graphviz's. The trade is accuracy + reproducibility over editorial polish.
